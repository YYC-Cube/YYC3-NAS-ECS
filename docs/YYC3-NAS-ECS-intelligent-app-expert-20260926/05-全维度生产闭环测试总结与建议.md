## 二、前端审计发现（评级 55-60/100）

### 2.1 健康面 ✅

- 13 条路由与侧边栏菜单一一对应，无缺漏
- api-v2 服务层设计到位：Mock/Real 工厂、限流（100 req/min）、30s 超时、XSS 响应消毒
- 三环境配置框架（dev/staging/prod）完整；零 TODO 残留、零密钥泄漏
- MonitorPanel 三态实践最好（isConnected/connectionMode 降级指示）

### 2.2 病灶 🔴 复制式演进残留（约 30-40% 代码不可达）

| 问题 | 明细 |
| ---- | ---- |
| 三套 API 客户端并存 | `api.ts` 与 `api-new.ts` 几乎逐行相同且**同名导出 `apiV2`**，均无人引用（纯死代码）；仅 `api-v2.ts` 在用（且只有 Mailbox/APIModule 两页消费） |
| 孤儿页面/组件约 20 个 | EmailApp(478行)、LayoutDemo、ComponentShowcase、DataDashboard、DocQualityDashboard、SystemDocumentation、email/EmailService、Navigation、ModuleButton/Table/Badge/Breadcrumb/Checkbox/Progress/SearchBox/Tabs 组件族、config/ConfigManager（与 frp/ConfigManager 双胞胎）、rbac/RBACManager（与 system/RBAC 双 RBAC）、双 ThemeContext |
| Python 蓝图混入 src | `src/app/api/v2/{llm,mail,nas,frp}.py` 等 5 个后端文件错位在前端源码树 |

### 2.3 病灶 🟠 基础设施断线

| 问题 | 明细 |
| ---- | ---- |
| 无路由库 | `useState` 伪路由：无 URL 同步、无深链接、刷新回首页、浏览器前进后退失效 |
| ErrorBoundary 完全缺失 | 全 src/ 零匹配——任何渲染异常直接白屏 |
| PWA 链路断裂 | `pwa/register.ts` + PWAInstallPrompt/UpdatePrompt 全部零调用，更新提示永不触发；无 vite-plugin-pwa，SW precache 不随构建更新 |
| i18n 未初始化 | react-i18next 依赖与语言包在库中但从未接线 |
| 12 个环境变量死声明 | vite-env.d.ts 声明但无消费（VITE_ENABLE_PERFORMANCE_MONITORING 等） |

### 2.4 病灶 🟠 接线不一致

- DDNS/NAS/LLM/frp 四个核心页面**绕过服务层裸 fetch**（28 处相对路径 `/api/...`），不走 envConfig per-service URL、不受 Mock 开关控制（冒烟实测 LLM 页因此报错）
- 监控页硬编码 `useWebSocket('ws://mock')` 伪协议，数据来自钩子内 mock
- frp/ConfigManager 硬编码公网 IP `8.152.195.33`；NasManager 假数据 `192.168.1.100`；useLLM 纯 mock 假实现（含 `password123` 示例文本与 `localCXip` 拼写错误）

## 三、后端审计发现（评级 58/100，C+）

> **首要更正：主后端是 Flask**（flask_sqlalchemy + flask_jwt_extended + gunicorn），FastAPI 仅存在于 services/llm 独立小服务。

### 3.1 健康面 ✅

- 应用工厂 + **fail-fast 环境校验**（生产强制 DATABASE_URL/JWT≥32 位/弱密钥黑名单/CORS 白名单禁 `*`）属同类项目上乘水准
- 容器规范：多阶段构建、非 root、HEALTHCHECK、gunicorn gevent×4
- 数据库模型 6 表 + Alembic 迁移 + seed/CLI 齐备
- FRP 生产链路配置自洽（7 条代理与 7 个生产域名一一对应）

### 3.2 病灶 🔴 前后端契约大面积错位（系统性）

- **前端调用但后端不存在**：auth（登录/登出）、system/stats、logs、mail 全部 11 个、llm 全部 6 个 → 真实模式下 404
- **能命中但字段不可用**：后端统一 `{success, data}` 包裹而前端 `client.get<T>` 不解包；`currentIP` vs `currentIp` 大小写、`localIP` 命名、FrpStatus/SystemStats/NasInfo 结构完全不同
- 路由方法错位：前端 POST `/ddns/config` vs 后端 PUT；`/nas/service/start` vs `/nas/start`；`/nas/files` 缺前缀
- **monitoring 双蓝图冲突**：`monitoring.py` 与 `monitoring_api.py` 挂同一前缀且都有 GET `/system`，后者 4 端点永不可达
- WebSocket 蓝图从未注册，nginx `/ws/`→8443 为死链

### 3.3 病灶 🟠 服务完成度不均

| 服务 | 状态 |
| ---- | ---- |
| frp / ai | ✅ 成熟（ai 有完整 docker+CI+测试） |
| ddns | 🟠 可用但 24 处硬编码真实 IP，脚本双份维护，systemd 单元未入库 |
| llm | 🟠 演示态（纯模拟响应），CORS `*` + credentials=True |
| mail | 🔴 `require('../shared/status')` 指向不存在目录，**启动即崩** |
| redis API | 🔴 仅 5 行半成品（无限流之外的路由、无 listen），另有 2 处真实密码硬编码 |

### 3.4 病灶 🟠 工程化缺口

- api/ **零 pytest**（requirements-dev 声明了但没有任何测试文件），CI 无后端门禁
- 后端部署无自动化（CI 中 Docker/SSH job 已移除，三套部署脚本并存口径不一）
- 遗留物：`__init___new__.py`、`app_fixed.py`、弃用 `ddns.py`、`docker-compose.new.yml` 等"new/fixed"后缀双实现
- v2 端点 90% 返回 mock 数据，ORM 与 API 脱节；约 70+ 后端端点无前端消费者

## 五、问题分级清单

### P0（影响真实可用性，建议下一会话优先）

1. **统一 API 契约**：后端响应统一 `{success, data}` 并在前端 ApiClient 统一解包；逐端点对齐字段命名（currentIp/localIP/嵌套结构）
2. **补齐 404 端点**：auth、system/stats、logs、mail/*、llm/* 五大块（或前端先切换到 Mock 明示）
3. **删除两套死代码客户端**（api.ts、api-new.ts 同名导出 apiV2 极易误引）
4. **mail 服务修复**（shared 路径崩）与 redis API 半成品（补路由+listen 或下线）
5. **monitoring 双蓝图 /system 冲突**修复；注册或移除 WebSocket 死链

### P1（结构性健壮性）

1. 补 ErrorBoundary + 页面级 error 兜底 UI
2. 引入 react-router（或伪路由加 URL 同步），获得深链接/刷新保持
3. 四个裸 fetch 页面收敛到服务层（受 Mock 开关与统一鉴权管辖）
4. api/ 补 pytest 基线（health/auth/frp/ddns 至少覆盖）并接入 CI 后端 job
5. 硬编码清理：8.152.195.33×27 处、redis 密码×2、src 内 Python 文件迁出

### P2（技术债收敛）

 1. 清理约 20 个孤儿文件/组件树与双实现（ConfigManager/RBAC/ThemeContext）
 2. PWA：registerSW 接线 + vite-plugin-pwa（或整体移除，二选一）
 3. i18n：初始化或移除未用依赖
 4. vite-env.d.ts 声明与实际消费对齐（12 死声明清理）；删除 `@services` 死别名
 5. 按钮嵌套 button 的 DOM 合法性修复；部署脚本三套收敛为一套

## 六、一句话总结

> **生产闭环（构建→流水线→Pages→FRP 隧道→密钥安全）已全链路跑通且全绿，但管理面板的真实数据链路尚未闭环——前端 Mock 与后端契约大面积错位，当前系统是"部署可信、数据演示"状态；按 P0 清单完成契约统一后，即可从 64 分迈入真实生产可用。**
